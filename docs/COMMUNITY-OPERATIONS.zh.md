# 社区运营、独立安审与举报处理方案

2026-09-08 · 待负责人确认的方案，不表示有人已值守或独立审查已完成。仅覆盖碳基会所 / laozi.art。

## 先用现有工具

普通缺陷继续用 GitHub Issues，讨论用 Discussions，漏洞使用 GitHub 私密漏洞报告。先不购买客服系统，也不自建账号库。GitHub 的漏洞私报是独立于 SECURITY.md 的设置，恢复发布前须确认已启用、收件通知有人接收。[官方说明](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)

骚扰、隐私泄露等行为举报不应塞进公开 Issue，也不宜混入漏洞公告。初期优先使用负责人已有、只限指定处理者访问的专用邮箱；具体地址由负责人提供，验证收信后才在产品中公布。本轮不创建账号、不开新云服务、不公开联系方式。

## 职责不能用“去中心化”略过

| 角色 | 可以交给工具的事 | 必须有人承担的事 |
| --- | --- | --- |
| 项目负责人 | 收集指标、准备发布清单、故障定位 | 决定开放范围、发布与回滚、公开承诺 |
| 节点运营者 | 健康探测、资源限额、配置校验 | 提供设备和网络、处理断电、保障联系渠道 |
| 举报处理者 | 整理材料、验签、去重、脱敏提醒 | 判断事实、决定措施、回复及申诉 |
| 独立审查者 | 重现脚本、测试包、威胁模型辅助 | 独立判断与具名/可追责的审查结论 |

AI 可以辅助上述各角色，不能假装是独立第三方，也不自动裁定谁在骚扰、谁应被封禁。另一模型复核代码可以降低盲点，但不能标成独立安全认证。

## 中继运营：初期三个独立故障域

目标是三个分别运营的 bootstrap/router，不是同一台 Mac 上开三个进程。尽量分开电源、网络和管理员；既有设备优先，任何新增付费服务由负责人批准。当前正式节点不在本轮改动范围。

每个节点登记：公开 Peer ID、WSS 地址、协议版本、运营联系人、维护窗口、资源上限、最近健康检查。只使用 laozi.art 授权的子域或运营者自己的明确域名，不借 A2A 配置和凭据。

健康检查复用 `probe-public-relay.mjs`：TLS/WSS → Noise/Yamux → 身份匹配 → Circuit Relay 预约。内部诊断只走回环令牌端点；不向公网暴露诊断口、不输出私钥或消息正文。CPU、内存、连接数、预约失败率足以做第一轮告警，不采集用户对话做监控。

拟定告警规则：连续三次探测失败才通知值守者；恢复通知一次；维护时段明确标记。尚未创建定时任务，待联系人与值守方式确认后配置。不要把单台 Mac 休眠误报成全网离线，也不要把仍有一个节点存活当成三节点容灾已达标。

发生事故：先停止新增邀请/扩大规模 → 核对故障域 → 尝试其他已核验入口 → 人工决定回滚。版本升级必须核对协议；0.5.1 与 0.5.0 不能混成一个大厅，不把用户静默跨频道转移。

## 举报流程

1. 用户先本地屏蔽；如需举报，主动选择一条或少量相关签名证据，并说明时间、问题与希望采取的措施。不自动上传整段大厅历史。
2. 提交前提醒：证据含消息原文与 Peer ID；不要附密钥、完整邀请、身份证、住址或无关人的信息。严重隐私泄露材料只走私密渠道。
3. 收件后生成案件编号，记录接收时间和经手人。先验签与去重，再读内容；签名证明消息来源，不证明昵称、职业、年龄或指控属实。
4. 区分普通争执、刷屏、冒充、隐私泄露、明确威胁及安全漏洞。高风险事项升级给负责人；不要求工具自行作法律结论。
5. 处理者记录证据、适用规则、处理范围、持续时间和复查日期。争议案件尽量由第二人复核；当事处理者回避。
6. 私下通知相关人可披露的结果与申诉方式；申诉由未作原决定的人复查。公开透明度报告只汇总数量，不晒举报人和聊天原文。

响应时间为待确认目标：一般报告 72 小时内确认收到；明显正在扩散的隐私风险优先处理。没有值守人以前，不公开承诺 24 小时响应。拟定材料默认结案 30 天后删除、未结案每 30 天复查；实际保留政策与特殊保全需求由负责人确认，不偷偷无限留存。

## 去中心化条件下能做、不能做的事

现在已实现：本地屏蔽、签名证据导出、协议限速与接纳成本。

未来可做：用户主动订阅的签名屏蔽建议列表（发行者、理由码、适用房间、过期时间、序列号与撤回记录），节点运营者明确选择的连接/资源拒绝策略。两者默认关闭；列表必须有数量上限、过期、撤销和申诉，不含举报者资料。需另行设计与审查后实现。

不能承诺：删除所有节点已有消息；阻止对方换身份；中继一键封禁全网；屏蔽后数据不再经过你的节点。无匿名抗女巫共识的公共网格不能靠一个管理员列表解决这些问题。

绝不增加：隐藏的监听、解密、远程执行或绕过身份校验入口。中继的安全诊断不是后门。

## 用户需要做的最少几件事

- 指定一个最终负责人；早期可由你自己担任，并找一位能复核争议的备用联系人。
- 提供一个愿意接收私密行为举报的渠道，并确认谁可访问。是否公开该地址需要你批准。
- 确认 Mac 可以提供的在线时段、带宽/资源预算；邀请另外两位愿意独立运营的人。工具不能替他们承诺。
- 寻找至少一位不负责本轮实现、熟悉 TypeScript/libp2p/签名协议的审查者。优先志愿审查；如需付费，先由你确定预算。
- 审核行为准则、响应目标、保留期限和发布范围。涉及账号权限、联系人公开、预算、正式节点变更均在执行前请示。

这些决定之前，仍可继续本地验证和小范围受邀测试；不能宣称运营体系已经上线。
